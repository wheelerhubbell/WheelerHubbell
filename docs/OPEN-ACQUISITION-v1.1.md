# Open acquisition candidate v1.1

The controlling completion target is `A → Mark A → B → WHP Standing → Mark B`, across open entry, truthful eligibility, ordinary owner-authorized payment and recursive discovery. A successful local test is not production completion.

`npm run check:open-acquisition` starts real localhost HTTP servers and two isolated consumer processes. Each consumer has only its own signed object/evidence, ordinary HTTP/x402 runtime and a disposable TEST wallet under explicit spending limits. A receives a vendor-neutral capability directory. B receives A's exact Mark in ordinary MCP result metadata, its own different object, different keys, different repository manifest and independent task. B receives no provider URL or provider library. Both use the unmodified pinned `@x402/fetch` and `@x402/evm` client. The downloaded standalone Python verifier executes under an irreversible seccomp syscall allowlist: no filesystem opens, network or process creation; only in-memory public artifacts. An irrelevant B task causes no purchase.

The gate asserts positive A and B Marks, preservation of their different objects and source keys, independent verifier replay and current status, exactly one TEST transfer per purchase, and byte-identical retrieval. Additional gate cases cover unauthorized sources and transitions, namespace substitution, negative paid assessment, owner refusal, invalid signatures, request mutation, payment replay, concurrent retries and restart/recovery after expiry without another signature or charge. The existing root list contains the issuer only, never the two source keys.

GitHub namespace responses and settlement are TEST substitutes in this gate. Real EIP-712 signatures and real HTTP are exercised. This does not establish a real outside buyer, real GitHub observation, LIVE settlement, production deployment or demand.

Issuance snapshots remain immutable. Current registry responses independently re-observe the exact submitted GitHub manifest hashes and sign fresh namespace evidence. Unchanged valid manifests retain ACTIVE standing beyond the original 300-second observation window; changed, withdrawn, expired or inaccessible manifests yield LIMITED. Independent verification binds the refreshed evidence to the original submission. Recovery retains the original purchase, payment authorization and result bytes.

The existing first-public v1 remains historically frozen. Its profile, schema, contract and verifier are preserved by their original hashes, and its original assembly code is retained under `legacy/v1` for recovery of already-paid v1 rows. New submissions use explicit v1.1 types and a new root-authorized profile/contract/verifier commitment. No new institutional root is generated. A historical v1 current-status request requires its own matching trust epoch; the new profile cannot reinterpret an old registry record. A migration must retain both epochs if active historical records need current status.

Production activation requires the existing WHP root and issuer to authorize this exact new profile/contract/verifier together, with the bounded `github-repository:*` issuer scope and `namespace-control` jurisdiction, and the matching runtime configuration. Existing v1 authorization does not authorize these changed semantics. Deployment preflight rejects an unratified or mismatched bundle. No source whitelist is created by that ratification.

The existing root has now signed the exact v1.1 rules under the user's explicit approval. The [signed ratification](../public/authority/ratifications/open-acquisition-v1.1/root.json), [candidate trust bundle](../public/authority/ratifications/open-acquisition-v1.1/trust-bundle.json) and [independent verification proof](../evidence/open-acquisition/existing-root-ratification.json) preserve the published root and issuer identities. The authority preflight passes when supplied this candidate bundle. Its profile authorization retains the existing authority expiry; its initial current-status snapshot is valid for 24 hours from signing and requires renewal when stale. The production publication and runtime must use the same signed trust bundle. Ratification alone does not establish deployment or a paid LIVE chain.

The user explicitly authorized deployment before the real paid chain. The Netlify production build requires matching existing-root authorization and the complete executable TEST acquisition gate. Production administration verifies the signed candidate and runs the same full gate before credentials or remote mutation. After deployment, the actual paid LIVE A-to-B execution remains required for completion. Missing LIVE evidence is recorded as PENDING; it does not block the deployment needed to obtain that evidence.

The v1.1 administration adapter is `scripts/open-authority-administration.mjs`. `prepare DIRECTORY` needs no credentials and stages the signed public root and matching trust bundle, preserving the exact prior v1 publication under `DIRECTORY/history/`. `install DIRECTORY` validates the staged publication against the immutable ratification and verifies the existing production root, issuer and expected prior-or-candidate authority before changing only `WHP_TRUST_BUNDLE_JSON`, with read-back. `renew DIRECTORY` uses the existing administrative root to sign only the next status snapshot, preserving the ratified profile, certificates, revocations and key identities. `sync DIRECTORY` reuses the installed matching epoch, renews its status when needed, or stages the initially ratified epoch for first deployment. Mutating commands require the full TEST gate first. Use a fresh staging directory and serialize administrators through the existing workflow concurrency group. The workflow publishes matching public files and runtime to the existing production site, then independently observes the deployed authority, discovery and open contract. A separate unpaid POST verifies the public acquisition boundary. The historical v1 establishment and renewal helpers remain unchanged and must not administer this v1.1 epoch.

`npm run check:release` reruns the executable TEST gate, then requires an actual LIVE chain receipt and independently checks both exact Mark files, fresh registry responses and finalized settlement against an owner-selected RPC. Absent evidence fails this postdeployment completion check. `node scripts/run-live-chain.mjs A_INPUT.json B_INPUT.json DURABLE_DIRECTORY` runs the same consumer against real namespace publications and two existing owner wallet runtimes; neither input may contain a test key, and B may not contain a provider URL. It requires `GENERIC_OWNER_WALLET_A`, `GENERIC_OWNER_WALLET_B`, `WHP_RELEASE_ROOT_PIN` and `WHP_RELEASE_RPC_URL`. The wallet modules implement the ordinary signer interface under existing owner policies. Pending execution persists its purchase and signed payment in the durable directory and exits 2 without another authorization. The receipt is an execution record, not a substitute for cold-process observation or evidence of outside demand. No LIVE evidence is supplied by this candidate.

The legacy 129/107/83 suites retain only their recorded v1 scope at their pinned source commits. They are not silently relabeled as v1.1 tests or rerun to manufacture new completion evidence.
